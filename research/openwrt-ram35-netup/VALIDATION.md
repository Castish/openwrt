# Проверка RAM35

Аппаратный результат приведён выше. Исправлен порядок запуска после
аппаратного RAM34 отказа: AP была удалена пустой конфигурацией до подключения
клиента. Это не был подтверждённый отказ радио или CCMP.

- 36 свежих проверок настоящего OpenWrt/cfg80211/hostapd WPA2 в32МиБ QEMU.
- Общая с физическим helper lifecycle-библиотека: сеть UP до AP, подготовка
  идемпотентна до AP и запрещена при активной AP, после DHCP AP остаётся UP.
- Независимый WPA2-клиент проверяет PMK/PTK/MIC/AES unwrap, неверный MIC
  отвергается; две авторизации/один AP start,13 Linux/DHCP/IP/TCP проверок.
- 13 дополнительных команд проверяют пустую конфигурацию, настоящий STOP_AP
  и отказ helper сообщить об успехе после остановки.
- Память после normal stop6396KiB MemAvailable; один pinned SSH password login.
- Полный Linux-патч31 файла и32 C/header/ASM inputs неизменны.3576 native и13
  OEM ARM builder cases относятся к RAM34 и унаследованы по точным хешам,
  повторного запуска не было. Пакеты45/ELF66 и668112-байтовый DMA pool прежние.
- 86728 source entries восстановлены побайтно,601 rootfs entries восстановлена
  без host root/mknod, новые zImage/handoff/restart/layout проверены.

QEMU не воспроизводит реальные MCU/CCMP/RF/DMA. Ранний ifup reproduction test
не вызвал аппаратное удаление в QEMU; дополнительный regression инъецирует
именно пустую конфигурацию из лога владельца. Нельзя утверждать, что аппаратный
тайминг ifup полностью воспроизведён. Физические видимость SSID/рукопожатие
RAM35, DHCP и передача данных требуют проверки владельцем.
