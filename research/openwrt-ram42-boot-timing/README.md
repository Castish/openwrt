# RAM42: отдельные задержки запуска MCU и опроса AP

В RAM41 ядро загрузилось и точные таймеры заработали на плате: 64 ожидания
на 1 мс заняли в среднем 1,223 мс. Подготовка Wi-Fi остановилась раньше
загрузки основной firmware: MCU достиг ready, но запрос управления остался
без подтверждения (`C80_OWN_TIMEOUT=8`). Host DMA не запускался, MCU остановлен,
очистка прошла без ошибок. Этот результат определяет место отказа, а не его
внутреннюю причину.

RAM42 сохраняет HIGH_RES_TIMERS и вводит явное разделение ожиданий:

- При инициализации и остановке короткий сон составляет не меньше 10 мс.
- Перед единственным начальным запросом управления предусмотрена пауза 10 мс.
- Во время работающего AP (phase 37) остаются запрошенные точные задержки:
  1 мс между проходами опроса, 50 мкс при ожидании некоторых ответов команд.

Предел ожидания управления остаётся 2 секунды. Повторных запросов, новых
регистровых команд и подмены подтверждения нет. Пауза — проверяемая гипотеза;
минимальная задержка, требуемая реальной firmware, пока не установлена.

Радио, пакеты MCU/DMA, WPA2-PSK/CCMP, проверка повторов и обработка клиентов
сохранены. Имя сети C80-RAM42, пароль openwrt123, канал 1, MTU 1400. AP всё
ещё передаёт данные на CCK 1 Мбит/с; скорость передачи клиента не измерена.
Точный таймер не устраняет время передачи больших кадров на этой скорости.

## Обновление

В корень прежнего TFTP-сервера скопируйте четыре файла:

- c80-openwrt-ram42-boot-timing-zImage
- c80-openwrt-ram42-boot-timing.dtb
- c80-openwrt-ram42-handoff.bin
- c80-auth.cpio

Последним замените c80-start.txt. Через LAN1 SSH выполните обычный `reboot`.
После загрузки снова подключитесь к 192.168.0.1, root / openwrt:

```sh
uname -r
c80-wifi start
c80-wifi status
```

Ожидаемое ядро: `6.12.113-c80-openwrt-ram42-boot-timing`. Если подготовка
снова завершилась ошибкой, сразу сохраните `c80-wifi report`; повторный start
или перезагрузка до отчёта не нужны.

Если AP работает, подключите один компьютер к C80-RAM42, IPv4 автоматически.
В PowerShell запустите прежний сценарий, приложенный без изменений:

```powershell
.\c80-wifi-load.ps1
```

После завершения или ошибки сценария через LAN1 выполните команды отдельно:

```sh
c80-wifi stop
c80-wifi status
c80-wifi report
```

Отчёт собирайте после Finished в status. Пришлите его целиком вместе с
результатом Windows. Он содержит C80 timers v1 и новые строки timing:
время достижения ready, фактическую паузу перед запросом управления, время
ответа и количества ожиданий при инициализации/работе/очистке. Чтение отчёта
использует сохранённые данные и не обращается к MMIO.

Сохраняется один клиент, без повторного запуска AP в той же загрузке,
WPA3/PMF/5 ГГц/HT/VHT и активной смены PTK. Новая запись U-Boot/NOR не нужна.
Индивидуальная SSH-идентичность сохранена. Персональный ZIP и c80-auth.cpio
содержат ключи этого роутера и не предназначены для публичного Git.

## Проверка

Новые проверки исполняют реальную функцию начального ownership на модели
MMIO/MCU и часов: ранний непринятый запрос в модели, успешное подтверждение
после паузы, уже полученное управление, all-ones, остановившиеся/обратные часы,
слишком раннее завершение сна, сохранение двухсекундного отказа без повторов,
раздельные задержки инициализации и активного AP. Модель не доказывает причину
отказа реальной firmware. Полный прежний набор native ASan/UBSan запускается
заново с новым общим кодом.

QEMU проверяет фактические ARM-обработчики отчёта, hostapd/nl80211/WPA2,
DHCP/IP/TCP и Linux-таймеры. Реальные MCU, DMA, аппаратный CCMP и радио QEMU
не моделирует. Отдельно проверяются код декомпрессора/handoff/restart, границы
размещения, восстановление Linux из исходного архива и полного патча, rootfs
и зависимости библиотек. Точные результаты и хеши находятся в PROVENANCE.json
и package-manifest.json. Аппаратный результат RAM42 при выдаче ещё отсутствует.

Публичные шаблоны rootfs находятся в overrides/. Персональный SSH overlay,
бинарные образы и OEM-входные файлы в Git не входят. Зависимости описаны в
../../docs/BUILD.md. Исходники прежних этапов и выданные теги сохранены.
